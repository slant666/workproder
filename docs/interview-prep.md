# 面试准备：Work Order System

## 一分钟项目介绍

这是一个内部工单管理系统，目标是把“用户提交问题、管理员分配和处理、用户确认完成”的流程做成一个完整闭环。前端使用 Vue 3、TypeScript、Element Plus，后端使用 Spring Boot 3、Java 21、JDBC、MySQL 8，数据库结构由 Flyway 管理。项目包含本地开发方式、Docker Compose 一键部署、后端和前端自动化测试。

我重点做了三类事情：第一是业务闭环，包括注册登录、工单创建、分配、状态流转、评论附件和操作日志；第二是权限和安全，包括普通用户和管理员权限隔离、CSRF、防暴力登录、密码哈希、会话刷新；第三是可交付性，包括 README、Docker 部署、测试和备份恢复说明。

## 三分钟讲解稿

这个项目的业务背景是内部支持或运维工单。普通用户遇到问题后创建工单，管理员负责查看、分配处理人、接单处理，处理完成后提交给用户确认。用户可以在详情页查看操作日志、评论、附件，并最终确认完成。

技术上，前端是 Vue 3 单页应用，使用 TypeScript 和 Element Plus 做表单、列表、筛选、分页和管理页面。后端是 Spring Boot 3，使用 Spring MVC 暴露 REST API，使用 JDBC 访问 MySQL。数据库迁移使用 Flyway，所以表结构可以随版本演进。部署上提供 Docker Compose，把前端 Nginx、后端、MySQL 拆成三个容器，数据和上传文件通过 Docker volume 持久化。

权限设计上，我把用户分为 USER 和 ADMIN。普通用户只能看见和操作自己相关的工单；管理员可以看管理页、用户管理、全部工单和统计。状态流转不是随便改字段，而是通过接单、提交确认、退回、确认完成、取消这些明确动作来完成，并且每个动作会检查角色、处理人和当前状态。

安全上，密码使用 BCrypt 哈希；登录态用 Session；所有会修改数据的 API 都有 CSRF token；登录连续失败会限流；登录成功后刷新 session id 和 CSRF token；附件下载加了 nosniff，Nginx 不对外暴露 actuator。测试方面，后端用 JUnit 和 H2 覆盖服务和控制器规则，前端用 Vitest 覆盖关键交互，当前完整测试可以一键运行。

如果继续扩展，我会优先补 OpenAPI 文档、CI、文件魔数校验、通知机制、Redis 限流/Session、以及更细的审计查询。

## 核心亮点

- 做的是完整业务闭环，不只是增删改查。
- 权限判断落在后端服务层，前端隐藏按钮只是体验优化。
- 状态流转通过明确动作驱动，避免任意修改状态。
- 有 Flyway 迁移、Docker Compose、自动化测试和部署文档。
- 安全项覆盖了密码哈希、CSRF、登录限流、会话刷新、附件下载头。

## 常见追问和参考答案

### 1. 为什么没有用 JPA，而是用 JDBC？

这个项目的数据访问逻辑相对明确，我希望 SQL 和索引使用更透明，所以选择 JDBC。这样在列表筛选、统计查询、权限过滤时可以更直接地控制 SQL。缺点是样板代码更多，如果实体关系继续复杂化，可以考虑 MyBatis 或 JPA。

### 2. 普通用户和管理员权限怎么保证？

前端会根据角色隐藏入口和按钮，但真正的权限判断在后端。后端每个需要登录的接口都会从 Session 取当前用户，再由服务层按角色、创建人、处理人、工单状态判断是否允许操作。这样即使有人绕过前端直接调接口，也不能越权。

### 3. 工单状态为什么设计成动作，而不是直接传 status？

直接传 status 容易绕过业务规则，比如从待处理直接改成已完成。现在用 accept、submit、return、confirm、cancel 这些动作，每个动作绑定允许的当前状态、角色和处理人规则，业务含义更清楚，也更容易测试。

### 4. CSRF 是怎么做的？

后端提供 `/api/auth/csrf` 生成并保存 session 级 token。所有非 GET/HEAD/OPTIONS 的 `/api/**` 请求都必须带 `X-CSRF-Token`。前端通过统一的 `apiFetch` 自动获取和携带 token。登录成功后后端刷新 session 和 token，前端也会清掉旧 token，下一次写请求重新获取。

### 5. 登录暴力尝试怎么处理？

后端按用户名记录失败次数，连续 5 次失败后锁定 15 分钟。错误密码、用户不存在、用户禁用都返回统一登录失败信息，避免暴露账号状态。当前实现是单 JVM 内存限流，后续多实例部署应迁移到 Redis。

### 6. 附件上传下载怎么保证安全？

当前实现做了大小限制、权限校验、随机存储文件名和下载权限校验。下载时加了 `X-Content-Type-Options: nosniff`。已知还可以继续增强文件魔数校验、病毒扫描、对象存储和临时签名 URL。

### 7. 数据库怎么演进？

使用 Flyway 管理迁移脚本，表结构从用户、工单逐步扩展到处理人、分配记录、状态流转、操作日志、评论、附件、用户管理审计。这样新环境启动时可以自动建表，旧环境也能按版本升级。

### 8. Docker 部署解决了什么问题？

Docker Compose 把前端 Nginx、后端、MySQL 拆成独立容器，一条命令启动完整环境。MySQL 数据和上传文件用 volume 持久化，密码通过 `.env` 提供。它不会影响宿主机已有 MySQL，因为容器 MySQL 默认映射到宿主机 3307。

### 9. 你怎么验证业务规则没有被改坏？

后端有服务层和控制器层测试，覆盖注册登录、权限、工单创建修改、查看权限、状态流转、分配处理人、评论附件和参数异常。前端测试覆盖登录注册错误提示、权限隐藏、创建修改校验、详情错误不泄漏内容、评论附件按钮权限。每次修复后运行完整后端和前端测试。

### 10. 项目还有哪些不足？

不足主要有：API 文档还不是自动生成；文件上传安全还可以做更深检测；登录限流目前是单实例内存实现；统计查询和分页在大数据量下还可以优化；前端组件可以进一步拆分；还没有 CI。

### 11. 如果要上线，你会优先做什么？

我会先补 CI，保证每次提交自动跑测试；接入 OpenAPI；把限流和 Session 外置到 Redis；加强上传文件校验和存储；补充生产级日志和审计查询；同时根据真实访问量做慢查询分析和索引调整。

### 12. 这个项目最能体现你能力的地方是什么？

我觉得是把业务规则、安全边界、测试和部署一起考虑。不是只把页面和接口跑起来，而是明确谁能看、谁能改、状态怎么走、异常怎么反馈、怎么部署、怎么验证。

## 模拟面试官提问与整合答案

**面试官：请你介绍一下这个项目，以及你在里面主要负责什么。**

可以这样回答：

这个项目是一个内部工单管理系统，覆盖普通用户提交工单、管理员分配处理、处理人推进状态、用户确认完成的完整流程。我主要完成了前后端功能、权限规则、安全加固、测试补齐和 Docker 化部署。

技术上，前端使用 Vue 3、TypeScript、Element Plus，后端使用 Java 21、Spring Boot 3、JDBC、MySQL 8，数据库迁移用 Flyway。部署上用 Docker Compose 管理 Nginx 前端、Spring Boot 后端和 MySQL 容器。

业务上，我比较关注权限和状态规则。普通用户只能访问自己相关的工单，管理员可以管理用户和全部工单；状态不能随意改，只能通过接单、提交确认、退回、确认完成、取消这些动作流转。安全上做了 BCrypt 密码哈希、Session 登录、CSRF token、登录失败限流、会话刷新和附件下载安全头。

测试方面，后端用 JUnit 覆盖服务和控制器规则，前端用 Vitest 覆盖关键交互。目前完整测试可以一键运行。这个项目目前还不是生产级系统，后续我会继续补 OpenAPI、CI、Redis 限流/Session、文件魔数校验和性能优化。

**面试官：如果我直接调接口，能不能越权看别人的工单？**

可以这样回答：

不能只依赖前端隐藏按钮。我的权限判断放在后端服务层。每个接口会先从 Session 拿当前用户，再根据用户角色、工单创建人、处理人和当前状态判断是否可见或可操作。普通用户访问不属于自己的工单详情、评论、附件时会被拒绝；管理员才有全局管理能力。

**面试官：你遇到过什么真实 bug？怎么处理的？**

可以这样回答：

在做登录限流时发现一个真实 bug：失败计数会被过早清掉，导致连续失败次数累不到锁定阈值，限流实际失效。我通过新增测试复现：连续 5 次错误后，第 6 次即使密码正确也应被临时锁定。然后修正清理逻辑，只在锁定期过后清理记录，最后跑完整测试确认没有回归。

**面试官：这个项目如果数据量上来会有什么问题？**

可以这样回答：

目前列表是常规分页，统计查询也是直接查库，适合学习项目和小规模内部系统。数据量上来后，我会先用慢查询日志和执行计划确认瓶颈，再优化组合索引、统计查询聚合方式，必要时做缓存、异步统计或游标分页。不会在没有数据支撑的情况下虚构性能指标。
